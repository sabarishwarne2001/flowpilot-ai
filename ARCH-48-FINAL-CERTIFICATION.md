## 1. What was built

**Two reviewers can never both decide one item — on every plan — and on Enterprise the review hub is live.** The hub (ARCH-40's nine kinds: EXTRACTION, ASSERTION, ANOMALY, MERGE, SPLIT, TABLE, CORROBORATION, OBLIGATION, POSTING) now carries a version per item; whoever decides with an older version, or while someone else holds the item's lock, is refused with a 409 that says why. With the capability, every console open on a workspace's hub shares one live channel: who is looking at which item (avatars), who is deciding it (a lock badge, taken when Resolve opens), decisions and assignments made anywhere (the row updates in place), and discussion threads anchored to the item, one of its fields or one paragraph of its document.

**Optimistic concurrency at the one entry point.** `resolution.resolve_item` — the single path every kind takes from the hub, one at a time (`resolve_scoped`) or in bulk — first takes the item's TURN (`_claim_turn`): a row lock on `review_item_versions (kind, item_id)` (`INSERT … ON CONFLICT DO NOTHING`, then `UPDATE … SET version = version + 1 … WHERE version = :expected RETURNING`), then it reloads the item and refuses one already resolved (`ALREADY_RESOLVED`), one locked by someone else (`LOCKED`, the holder named) and a stale expected version (`STALE_VERSION`); only then does the kind's own handler (`_DISPATCH`, all nine kept) run, in the same transaction. The second of two concurrent reviewers waits on the row lock and then finds the version moved or the item resolved. The version also protects an item that was decided and came back OPEN under the same id (an ERP posting retried and failing again): a reviewer still looking at the earlier exception is refused `STALE_VERSION` instead of deciding the new one blind. A caller that sends no version (the API keeps that optional, so existing clients keep working) is still serialised and still refused an item already resolved or locked. **Bulk** resolves item by item inside SAVEPOINTs, in canonical (sorted id) order so two bulk requests can never deadlock, reports `STALE_VERSION` / `LOCKED` / `ALREADY_RESOLVED` per item and commits the rest. **The source screens** decide hub items without `resolve_item` (anomaly confirm and dismiss, table review, corroboration comparisons, obligations, ERP posting review, packet split approve and reject): those eight routes call `review_api.decision_guard` first, so a lock or a decision made in the hub is respected there too.

**Soft locks.** `review_locks`: one live holder per item (UNIQUE (kind, item)), a lease token and an expiry. Acquiring is one statement — `INSERT … ON CONFLICT (kind, item_id) DO UPDATE … WHERE the lease has lapsed OR it is already mine` — so of any number of concurrent lockers exactly one holds it. A heartbeat extends only the caller's own unexpired lease (`GREATEST`, so a lease never moves backwards); a lapsed lease is free and its old token never revives it. The lease lasts 90 s past its last heartbeat (the console pings every 25 s: three missed pings, not one, cost the lock), and the database bounds any lease to ten minutes past its heartbeat (CHECK), so no bug can make a lock outlive its holder. Resolving clears the item's lock and announces it; a workspace ADMIN can break a lock (audited); a clean close of the connection (the console unmounting, a tab closing) releases the holder's locks; an abnormal one (a dropped network) leaves them to expire, so a brief disconnection does not cost the lock — the console re-takes what it held when it reconnects.

**The live channel.** One WebSocket per console: `GET /api/v1/workspaces/{id}/review/collab/live`. It authenticates with the SAME access token the REST client sends — no new auth scheme — carried in the subprotocol list (`["flowpilot.review.v1", "bearer.<token>"]`): a browser cannot set `Authorization` on a WebSocket and a query string lands in every access log, so a query-string token is refused, as are API keys. Before accepting, the handshake checks the host (ours or a verified custom domain), the Origin (same site; opaque origins refused), the token, the session (revocation and "signed out everywhere"), the organization's operational state, workspace access, CONTRIBUTOR and the capability — every check the REST dependency makes, plus the plan. A refusal is a close BEFORE accept, which a real server sends as an **HTTP 403** (Starlette's test client reports it as close code 1008). An accepted connection is re-checked every minute and closed 4401 (token expired, session revoked: the console refreshes and reconnects) or 4403 (access or plan gone); 1009 for a frame over 4 KiB, 4429 over 40 messages in 10 s, 12 connections per person per process. The server selects the subprotocol and never echoes the token entry.

**Fan-out across API workers through Redis** (already running; no new service): one pub/sub channel per workspace, presence as a Redis hash with a 75 s TTL per viewer, and a per-workspace leader lease. The leader expires lapsed locks every 5 s (announcing `lock.released` with reason EXPIRED) and watches a digest of the queue, so a change made where no event is raised (an upload, a worker finishing) still reaches every console as `queue.changed`. Events are published only AFTER the transaction that caused them commits (`collab.events.publish_after_commit`, SQLAlchemy session events; a rolled-back SAVEPOINT drops what it queued; a broken Redis falls back to local delivery and never fails the write), and they carry ids and names only — never document text or comment bodies: consoles re-read through the gated REST routes. Without Redis (development), an in-process broker serves one worker.

**Discussion threads.** `review_threads` anchored to the ITEM, a FIELD, or a PARAGRAPH of the item's document: page, paragraph index, a quote and a 32-hex digest of the paragraph's normalised text. Paragraphs are cut with ARCH-45's segmenter (reading order; running headers and folios dropped), so the digest survives layout noise; after reprocessing an anchor is re-found where its text now is (MOVED) or shown as OUTDATED, and a thread posted against a paragraph whose digest no longer matches is refused (409 `ANCHOR_MOVED`). `review_comments`: idempotent per (thread, author, client nonce) so a retried submission never posts twice; @-mentions are workspace members only (an outsider is refused) and raise an in-app notification without the comment text; authors edit their own, authors or admins delete (moderation audited); threads resolve and reopen; each queue row shows its open-thread count. ARCH-20 erasure removes the subject's words from every thread (the row keeps its place), deletes discussions anchored on their documents (they quote them) and releases their locks; a document's deletion deletes its discussions.

**Data.** `review_item_versions`, `review_locks`, `review_threads`, `review_comments`. Composite FKs `(workspace_id, organization_id)`, `(work_item_id, workspace_id)` and `(thread_id, workspace_id)`; CHECKs for known kinds, lease order and bound, anchor shapes (NULL-safe — §7), resolution consistency, comment body vs deletion, and at most 20 mentions. Zero column drift between models and migration. The hub view (`review_queue_view_v8`) and the outbox vocabulary are unchanged: the projection joins the version and the open-thread count.

**API.** 10 REST routes under `/review/collab`, each gated on the capability as its first statement (402 `CAPABILITY_REQUIRED`, audited), CONTRIBUTOR (the lock break ADMIN): live state (presence and locks), threads of an item (list, start), an item's paragraphs, reply, resolve, reopen, edit and delete a comment, break a lock — and the WebSocket. The hub's existing routes gained `version` and `open_threads` on items, `expected_version` on resolve and `expected_versions` on bulk, and 409 envelopes with `STALE_VERSION` / `LOCKED` / `ALREADY_RESOLVED`.

**Console.** The review hub, for every plan, sends the version it read and explains a 409 (someone decided first — the row refreshes; someone is deciding — who). On Enterprise: a Live pill in the header (live / reconnecting / offline), avatars of whoever else has an item open, a lock badge while someone decides (opening Resolve takes the lock and heartbeats keep it; closing releases it; an admin's Break lock), live updates of resolutions, assignments and queue changes, and a discussion panel per item (item, field and paragraph anchors with a paragraph picker, MOVED / OUTDATED markers, @-mentions, edit, delete, resolve, reopen; keyboard `c`). The connection backs off exponentially with jitter, re-sends what it views and holds after a reconnect, probes REST when a handshake is refused (a 402 or 403 there stops retrying) and closes cleanly on unmount. The token never appears in a URL.

**Ingress.** `deploy/Caddyfile`: on the platform host and on custom domains, `/api/v1/workspaces/*/review/collab/live` is routed before `/api/*` with `flush_interval -1` and a five-minute `stream_close_delay` (a config reload does not drop every console at once), and both access logs delete `Sec-WebSocket-Protocol` (it carries the token).

## 7. Found and fixed during the build

- **A NULL-unsafe CHECK.** The first anchor-shape CHECK accepted a PARAGRAPH anchor with no digest: a CHECK refuses only FALSE, and `NULL ~ '^[0-9a-f]{32}$'` is NULL. Found by D3; every comparison in the CHECK is now paired with `IS NOT NULL` (MS8 re-introduces it and D3/T2 catch it).
- **A re-entrant lock acquire could violate the lease CHECK.** A second tab of the same holder re-acquiring with an older clock reading moved `heartbeat_at` backwards past `expires_at` (a CheckViolation under X1's race). `acquire_lock` and `heartbeat` now take `GREATEST` of the old and new instants, so a lease only moves forward (X2 step, MD18).
- **Two bulk requests could deadlock.** Resolving in request order took the version row locks in opposite orders; bulk now decides in canonical (sorted id) order and reports results in request order (X1).
- **Publishing on commit is subtle.** SQLAlchemy's `after_soft_rollback` does not say whether the ROOT transaction will commit, and a nested transaction's parent is cleared by the time it ends. Events are queued with the chain of transactions they belong to, dropped when any of them rolled back, and published only when the root commits (E1, MS15, MS16).
- **The hub's dispatch was not thread-safe.** Sync REST routes run in a thread pool; an event they raised waited for something else to wake the event loop. Dispatch now crosses with `call_soon_threadsafe` (B1 measures it under 0.5 s; MS20).
- **`resolution.assign` rolled back the caller's transaction** on a lost assignment race (`db.rollback()`), discarding whatever the request had done; it now uses a SAVEPOINT.
- **Collaboration audits on review items would have broken ARCH-40 B8**, which pins exactly two writers of `AuditResourceType.REVIEW_ITEM`; moderation and lock-break audits are recorded against the WORKSPACE with the item in their details.
- **The first full run (71 passed, 3 failed) — MD7, MD13 and MD14.** MD13 ("the lock claim takes over a live lease") failed with a lease CheckViolation instead of its expected reason. Tracing it found the re-entrant-lease bug above: a holder re-acquiring with an earlier clock reading (a second tab) moved `heartbeat_at` backwards — a bug in the unmutated claim too. Fixed with `GREATEST`; an X2 step and MD18 now gate it. MD7's D6 batch assigned each item's role (decided, stale, locked) by its position in the request, which the canonical processing order made unreliable; roles now follow the sorted ids. MD14 rebuilt the service module from source, so the mutated copy read its own clock rather than the gate's pinned one and failed for the wrong reason; `variant(..., link=("now",))` links the clock back. After the fixes: 79/79.
- Harness corrections recorded because they are traps: the race gates need their own engine (`pool_size = N + 2`; the app pool times out) and must prepare every session BEFORE the barrier; a mutation that rebuilds a module must link the module's clock back (`variant(..., link=("now",))`) or it reads its own copy and fails for the wrong reason (MD14's first run); websockets 15's client needs `proxy=None` behind the sandbox proxy; a Starlette `TestClient` WebSocket closed without an explicit code is cancelled, not closed cleanly.

## 8. Corrections to the prompt and roadmap

- **"Close with a policy code (1008) before accepting."** On a real server (uvicorn, and so Caddy) a close before accept is an **HTTP 403** response to the upgrade; 1008 is what Starlette's test client reports. The gates check both, and the console treats a handshake that never opened as refused only after a REST probe says 402/403 (otherwise it retries).
- **"A version column" and "tables `review_locks`, `review_threads`, `review_comments`".** A version column would have to be added to nine source tables of nine milestones; the version lives in a fourth table, `review_item_versions (kind, item_id)`, which is also the row the turn locks. The hub view is untouched.
- **"Enforced at the one entry point `resolution.resolve_item`."** Necessary but not sufficient: eight source-screen routes decide hub items without it. They are guarded too (`decision_guard`), or a lock taken in the hub would be ignored on the obligation or packet-split page.
- **"Authenticated with the existing session (the cookie/bearer the REST API already accepts)."** The REST API accepts a bearer access token only (the refresh cookie is scoped to the refresh route). The live channel accepts that same token — in the subprotocol list, since a browser cannot set `Authorization` on a WebSocket — and re-applies every session check the REST dependency makes.
- **`ARCH-47-HANDOFF-PROMPT.md` and `ARCH-48-HANDOFF-PROMPT.md` were not in 7680b0c.** ARCH-47's apply creates them but they were never committed; ARCH-48's apply carries both with ARCH-47's canonical text (and accepts the ARCH-48 prompt as the project stores it).
- **Optimistic concurrency is not an Enterprise feature.** Double resolution is a data-integrity bug on every plan, so versions, locks' refusals and the 409s apply to every plan (D4 proves it without the capability); only the live channel, presence, taking locks and threads are gated.

## 9. Not run in the sandbox

- **This package on Windows.** The sandbox is Linux: `run_arch48.ps1` and `npm.cmd install` ran only as their Linux equivalents. Nothing in ARCH-48 depends on path syntax; the in-process servers are addressed as `127.0.0.1`.
- **A browser.** The console is type-checked, built and linted and its protocol exercised by real WebSocket clients (Starlette's test client, the `websockets` library through two uvicorn processes and through Caddy), but no browser drove the page. The gates send `Origin` and the subprotocol list the way a browser does.
- **Redis Cluster / Sentinel and multiple hosts.** Fan-out was proved across two processes on one host against one Redis 7.0 (the production pin is redis-py 8.1.0, as used here).
- `scripts/verify_arch10_step3.py` / `verify_arch10_step9.py` — not run (never against a database you back up). `verify_hardening_master --db` D1/D5/D6/D7 and `verify_hardening_final --db` "Payment loop (Stripe)" — not run; they need real gateway price ids and webhook secrets.
- Committed organizations left in the development database by early, failed runs of the committed gates stay there: they had written audit rows, and `audit_logs` refuses DELETE. Every passing run deletes its own.

## 10. Deploying

From the repository root: `.\run_arch48.ps1` (add `-AllowUnpriced` on a development database; `-SeedPriceBook` on a fresh one). It checks, applies (and proves a second apply writes nothing), confirms `websockets`, `redis` and `uvicorn` (already pinned) and that Redis answers at `REDIS_URL`, migrates to `arch48_step1_collaborative_review` (stamping around an already-run contract step), seeds an Enterprise tier version carrying `capability.collaborative_review` (`--carry-forward` moves live subscriptions), validates the Caddyfile with the real Caddy when one is on PATH or in `$env:CADDY`, installs the console and runs the full certification. **Every API worker needs `REDIS_URL`** (without it each worker's consoles only see that worker's events). Reload Caddy with the new Caddyfile. Nothing new to schedule, no new worker job. Rollback: `.\run_arch48.ps1 -Rollback` (code), then `alembic downgrade arch47_step1_erp_posting` (database: drops the four tables; nothing else changed).
