## 1. What was built

**An object-centric event log of how work actually flows, what it costs and where it will miss its target — and an agent that proposes how to clear the exceptions, governed so it acts on its own only where ARCH-35 has measured that it may.**

**The event log** (`process_events` + `process_event_objects`; ids, enums and numbers only — no document text, filenames, headlines, error messages or comment bodies ever enter it). Built incrementally by the sweep from **17 sources**: `work_items` (uploaded, pipeline stage, retention holds), `jobs`, a whitelist of INTERNAL `outbox_events` the state tables do not record, `audit_logs` (hub decisions, lock breaks), the review hub's nine kinds through `review.projection`, `review_assignments`, `review_locks` (live ones), `review_threads`, `automation_executions` and `automation_node_runs`, `cases`, `case_documents`, `case_rule_results`, `erp_postings`, `erp_posting_attempts`, `anomaly_findings`, and the agent's own proposals. Each source is keyset-paged on `(timestamp, key)` per workspace with a per-source cursor; a caught-up source also re-reads a bounded two-hour overlap behind its cursor (a row committed late with an earlier timestamp is still found) without moving the cursor; every event has a `(source, source_key)` unique across all time and is written `ON CONFLICT DO NOTHING`, so re-reading never writes twice; a per-workspace advisory transaction lock serialises concurrent sweeps; events are pruned at 400 days (`audit_logs` itself is never touched).

**Discovery and conformance.** Per object type (documents, cases, ERP postings, review items, radar findings, flow runs): the directly-follows graph with counts and median waits, starts and ends, variants with share, median throughput, cost and touches, rework, and an object's full timeline across every object it shares events with. Events at the same instant follow the lifecycle (a document's upload first, then beginnings, then progress, then endings), never their row ids. Conformance replays tokens (consume-all joins, choice splits) against every ARCH-37 flow's current graph (executions before the last edit set apart) and every ARCH-43 case template's slots, with fitness and where tokens went missing.

**SLA-breach prediction.** Per object type with an SLA (review items 24 h, cases 168 h, postings 4 h by default; an admin sets target, at-risk threshold and alerting): `HistGradientBoostingClassifier` (scikit-learn 1.9.0, already pinned) on LANDMARK snapshots taken at fixed ages — so a feature can never see the outcome — with a fixed hash-based held-out fifth. A run is ACCEPTED only when its Brier score beats the base rate's by at least 0.02 skill (a DB CHECK forbids an ACCEPTED run that does not beat its baseline); otherwise it is REFUSED with its reason, and nothing is predicted. Reliability bins and permutation importances are stored with the run. An at-risk open object raises the new automation trigger **`process.sla_at_risk`** once per (object, due time) — ids and numbers only — so flows can act on it. What the log records of process intelligence's own outputs (the alert, the agent's proposals) is never a feature (§7).

**Cost to serve** from ARCH-18/24's cost truth: each object's documents' metered usage, priced from the cost basis, scaled by `invoiced / modelled` where a supplier reconciliation is MATCHED or ACCEPTED for that provider and period; a metered event with no settled cost is counted as UNKNOWN (with its share of charges shown), never summed as zero.

**The exception agent** is model-free: no LLM call, no outbound host. Each sweep it plans over the hub's open items, inconsistent cases (re-evaluate; request the missing document through a single-use upload link) and failed postings (retry a transient failure; route an UNCERTAIN one to its owner — never a blind retry): 13 proposal kinds in all. Typed READ tools (15) gather ids, states, scores, precedent counts and calibrated probabilities; four ACTION tools (`agent.resolve_review_item`, `agent.assign_review_item`, `agent.reevaluate_case`, `agent.request_case_document`) are registered through ARCH-33's `fenced_context.register_tool_selector`, which refuses a `FencedContext`, a dict or an unannotated parameter by type. A proposal is a typed `AgentAction` (tool, kind, a verdict from the kind's closed set, the item's id and the version it read, a template key with numbers — no free text), with every tool call recorded in `agent_tool_calls`. Document text is read only to be quoted back to a person, fenced (`FencedContext`, a per-response nonce) and scanned by the injection scorer; a suspected injection holds a proposal for a person. One live proposal per item (partial UNIQUE); a proposal a person rejected or undid, or that failed, is not made again for the same item version.

**Applying.** Approve applies through the owning service — `resolution.resolve_item` with the version the agent read for every hub kind (so ARCH-48's turn, lock and version checks bind the agent for free), ARCH-43's case service and the ERP retry for the rest — under the proposal's row lock (`SELECT … FOR UPDATE`), so concurrent approvals yield one application and `ALREADY_DECIDED` for the rest. Reject needs a listed reason. A database refusal inside an apply is recorded FAILED in a savepoint; a person deciding the item first supersedes the proposal and their decision stands.

**Data.** Nine tables: `process_events`, `process_event_objects`, `process_ingest_cursors`, `process_sla_policies`, `process_model_runs`, `process_predictions`, `agent_policies`, `agent_proposals`, `agent_tool_calls`. Composite FKs to `(workspace_id, organization_id)`; CHECKs for the activity shape, known sources, objects and actors, only-calibrated-kinds-apply-themselves, ACCEPTED-beats-baseline, a refusal carries its reason, the hold bound (5–1440 min), no human decider on an automatic apply, a rejection carries its reason, a tool from the registry, a prediction due after it started. The outbox visibility CHECK gains one event; the hub view is untouched. Zero column drift.

**API.** 15 routes under `/workspaces/{id}/process`, each gated on the capability as its FIRST statement (402 `CAPABILITY_REQUIRED`, audited): overview, discovery, an object's timeline, conformance, SLA and cost (VIEWER); SLA policy per object type (PUT — ADMIN, audited); sweep now (ADMIN); the agent policy (CONTRIBUTOR to read; PUT — ADMIN, audited); proposals — list, one with its tool calls and fenced excerpts, approve, reject, undo (CONTRIBUTOR). **Wiring:** job `process.sweep_workspace` on the LIGHT worker profile; `scripts/sweep_process.py` enqueues one job per enabled workspace per 15-minute slot (idempotency key); `backend/deploy/bin/flowpilot-sweep process` and a line in `backend/deploy/cron.d/flowpilot-sweepers` (every 15 minutes). Live `proposal.changed` events through ARCH-48's channel (after commit, ids only).

**Console.** *Process intelligence* in the Enterprise-processing navigation (plan-gated like its API): Overview (the log, the breach models, a banner of what is at risk and waiting), Discovery (object type, window, the directly-follows graph as SVG, variants with cost and touches, examples linking to object timelines), Conformance (flows and case templates, fitness, where tokens went missing), Service levels (targets, thresholds, alerting; each model's Brier, skill, reliability and strongest signals; open objects by breach probability), Cost to serve, and the Exception agent (inbox by status; a proposal's evidence, every tool call, why a person decides or when it applies itself, the fenced source text as quoted text; approve, reject with a reason, undo during the hold; the policy panel). The review hub shows the agent's proposal inside an expanded item, with approve and reject there too, and refreshes on `proposal.changed`.

## 2. The five decisions the roadmap left open

1. **Where the event log lives: a materialized table, built incrementally.** Views cannot work: `outbox_events` is pruned, `case_rule_results` is rewritten on every evaluation and `review_locks` rows are deleted on release, so a view would forget what happened. `audit_logs` stays append-only and unpruned; the derived log is pruned at 400 days.
2. **Object identity per event: every event links to every object it touches** (`process_event_objects`: object type, object id, a qualifier such as `counterpart` for a finding's second document). The case notion is chosen at query time per object type — DOCUMENT, CASE, POSTING, REVIEW_ITEM, FINDING, EXECUTION — so one event (a finding raised on two documents, a posting attempt of a document in a case) counts in each object's trace. A review item is identified by its hub id; a radar finding and its review item share the source row's id and are told apart by type.
3. **Which kinds may apply themselves: read, never assumed.** Only kinds whose decision ARCH-35 automates can ever carry a conformal bound: `extraction.approve_consensus` (`verification.document`) and `assertion.accept_engine` (`assertion.*`). `anomaly.finding` is only MEASURED by ARCH-35 (`apply.decide` refuses it), so radar proposals always wait for a person; the other ten kinds have no calibration at all. Even for the two, auto-apply needs ALL of: the workspace policy on for that kind (off by default); its enabling admin still an active ADMIN (the resolution is recorded under their authority); the item held back by calibration alone (for a clause, the engine said PASS); no injection suspected; no open discussion; and the tenant's LIVE model read at that moment through `calibration.apply.decide` — ACTIVE, not stale, achievable (conformal bound ≤ the target), the calibrated probability at or above the threshold, and not drawn for an accuracy audit. The development database held **zero** `calibration_models` rows at certification; D10 builds them inside its rolled-back transaction.
4. **Undo = cancel during the hold.** An auto-capable proposal is AUTO_SCHEDULED with a hold (policy default 30 minutes, 5–1440), admins notified; anyone who may decide the item (CONTRIBUTOR) can undo it until it applies. When due, every condition is re-checked (a suspended model, auto-apply switched off, the owner demoted or gone each send it back to a person). An applied decision is reversed the way any hub decision is — on its owning screen — and an auto-applied decision is excluded from ARCH-35's labels and ARCH-41's extraction memory (label hygiene: the platform must not learn from its own decisions).
5. **`LOCKED`: wait, never break.** The agent has no lock-breaking tool (a gate checks). When `resolve_item` answers `LOCKED`, the proposal records `waiting_until` = the lease's expiry and is retried after it; the person's lock is untouched.

## 5. Packaging

`backend/apply_arch49.py` is generated from `git diff 5ac6496` plus the new files with ARCH-48's engine: sha-guarded `new` and anchored `edit` operations (each anchor occurs exactly once when applied; the result is checked against the final sha256), atomic (everything planned before anything is written; originals and modes kept in `.arch49_apply_backup/`), `--check` / `--rollback` / `--list`, and files a later milestone changed reported as superseded (`ARCH50-S1:` onward). The generator refuses to emit if any file carries no `ARCH49-S` sentinel. It owns **88 files: 43 new, 45 edited through 106 anchors** (447 KiB). Line endings, `navigation.ts`'s byte-order mark and UTF-16 files are kept as found; new files are written LF.

**Proof (`evidence/arch49/apply_proof.json`)** on a clean **LF** worktree of 5ac6496 and a **CRLF** copy (every owned text file rewritten to CRLF): `--check` plans 88 writes and writes nothing; the apply writes 88; a second apply writes 0; all 88 files equal the ARCH-49 tree (CRLF files stay CRLF); `--rollback` restores all 88 byte for byte and removes the new files and the backup; the LF tree is `git status`-clean afterwards. ## 7. Found and fixed during the build

- **The SLA alert fed back into its own prediction (found in the browser).** The alert is an outbox event, so the next sweep ingested it as the item's latest activity — one no finished item was trained on — and the at-risk items flipped to OK (0.993 → 0.349) on the sweep after they were alerted. What process intelligence writes into its own log (`vocabulary.SELF_ACTIVITY_PREFIXES`: `agent.*`, `sla.*`) is now mined and shown but never a feature (`sla.work_steps`); D8 ingests the alerts and requires the items still AT_RISK; MD14 re-introduces the loop and D8 catches it with exactly the smoke's symptom (`['OK', 'OK', 'OK']`).
- **Same-instant ordering put a finding before its document (found in the browser).** Upload, "finding raised" and "review opened" were all "beginnings", tied by random row ids, so 45 % of document variants began with the finding. A document's upload now precedes every other beginning at its instant (T4, MS30).
- **Console defects (found in the browser):** the graph's arrowheads scaled with edge width (`markerUnits` now `userSpaceOnUse`); edge labels were hidden under nodes and edges within one column were drawn through them (wider columns, haloed labels drawn last, same-column arcs on the left, rework in its own lane below); the SLA inputs' units wrapped under them.
- **Bind parameters inside SQL literals.** Source keys built as `id || ':opened'` were read by SQLAlchemy's `text()` as a `:opened` bind parameter; keys use `/`.
- **The overlap re-read reset the cursor.** The first design re-read the overlap by rewinding the cursor itself, so a caught-up source's position moved backwards (D5 caught it). The forward read and the bounded overlap re-read are now separate and the overlap never moves the cursor (MD2, MD3).
- **An ownerless policy crashed the apply.** A due proposal whose policy had no enabling admin reached the database without a decider (an IntegrityError — MD7 first failed for that wrong reason). It is now held `OWNER_NOT_ADMIN`, and any database refusal inside an apply is caught in a savepoint and recorded FAILED with the reason.
- **Declined proposals came back.** The planner re-proposed an item a person had rejected (or undone, or that failed) at the same version; declined (item, version) pairs are now skipped (D10: "the agent does not propose it again").
- **The sweep script enqueued outside a transaction**, and the enabled-workspace query carried a LIMIT (a large deployment would have skipped workspaces): `db.begin()` first, no limit, ordered.
- Harness traps recorded for ARCH-50: the fence preamble itself contains the marker text (J1 looks for `<<<SOURCE-{nonce} id=` and the LAST closing marker); a text mutation (`_with_file`) cannot reach a gate that imports the module — use `variant(...)` (MS30's first run "passed against broken code"); the committed gates need `backend/.env` in a fresh worktree; `exactOptionalPropertyTypes` needs `| undefined` on optional props.

## 8. Corrections to the prompt and roadmap

- **`resolution.resolve_item(db, context, kind, item_id, …)`** — the real signature is `resolve_item(db, *, item, actor_user_id, payload, expected_version=None)` with a LOADED item (`projection.load_item`); `resolve_scoped(db, *, workspace_id, kind, item_id, …)` is the (kind, id) entry point. The agent uses them with the version it read.
- **`publish_after_commit(db, event)`** — it is `publish_after_commit(db, workspace_id, message)`.
- **"Kinds with an ARCH-35 conformal bound … `decision.py`, `risk.conformal_threshold`"** — the live decision is `calibration.apply.decide`, which refuses decision types ARCH-35 does not automate; `anomaly.finding` is measured only, so the roadmap's radar findings can never auto-apply (§2.3).
- **"`review_item_versions` … as sources"** — the table holds only the current version (no history), so it is read for the version, not mined. **`review_locks`** rows are deleted on release: only live locks are observable; lock breaks come from the audit log. **`review_assignments`** holds one row per item (the current assignment).
- **"Built from the outbox …"** — the outbox is pruned and `case_rule_results` rewritten, which is why the log is materialized (§2.1).
- **The isolation test** that walks the tool selectors is `tests/services/test_arch12_budget_and_isolation.py`.
- **`verify_arch48`'s pins** (T2 chain, W1 trigger counts, MS5) had to be widened too, not only 31–47.

## 9. Not run in the sandbox

- **Windows.** The sandbox is Linux: `run_arch49.ps1` ran only as its Linux equivalents (apply, migrate, seed, build, verify). Nothing in ARCH-49 depends on path syntax.
- **The browser pass is a smoke, not a suite.** It covered every console page on one desktop viewport in light mode against a demo tenant; it is not part of `verify_arch49` (it needs a running API, a dev server and a committed tenant). Dark mode, small screens and an auto-apply countdown in a browser were not exercised (the auto-apply path is gated end to end at the API in D10).
- **Real ARCH-35 models.** No tenant in the development database has a calibration model; D10 proves the path against models it builds in its transaction.
- `scripts/verify_arch10_step3.py` / `verify_arch10_step9.py` — not run (never against a database you back up). `verify_hardening_master --db` D1/D5/D6/D7 and `verify_hardening_final --db` "Payment loop (Stripe)" — not run; they need real gateway price ids and webhook secrets.
- **Left in the development database:** the browser-smoke tenant ("Smoke Enterprise"), because logging in wrote audit rows and `audit_logs` refuses DELETE. Every verifier run deletes its own organizations.
- Observed, pre-existing, not changed: `/auth/me` answers 500 for a stored email on a reserved domain (`.test` — the response model's email validator refuses it; the smoke tenant's first address); and the console requests `/users/{id}/avatar` for users without one (a 404 per render).

## 10. Deploying

From the repository root: `.\run_arch49.ps1` (add `-AllowUnpriced` on a development database; `-SeedPriceBook` on a fresh one; `-CheckOnly` first if you like). It checks the tree, applies (and proves a second apply writes nothing), confirms scikit-learn 1.9.0 and numpy (already pinned), migrates to `arch49_step1_process_intelligence` — never `head`; if the contract step already ran it stamps around it — seeds an Enterprise tier version carrying `capability.process_intelligence` (`--carry-forward` moves live subscriptions), installs the console and runs the full certification. **Schedule:** the cron line is in `backend/deploy/cron.d/flowpilot-sweepers` (`flowpilot-sweep process --apply`, every 15 minutes; `HEARTBEAT_UUID_PROCESS` optional); the job runs on the existing LIGHT worker profile. No new service, dependency or recurring cost. Auto-apply is off by default; an admin turns it on per kind in the agent policy. Rollback: `.\run_arch49.ps1 -Rollback` (code), then `alembic downgrade arch48_step1_collaborative_review` (database: drops the nine tables, deletes the `trigger.process.sla_at_risk` outbox rows and restores the earlier outbox vocabulary; the hub view never changed).
